## Summary

Kafka Streams window and session state stores are internally divided into time-based segments, each backed by a separate RocksDB instance. The segment interval controls how wide each segment is in time. Currently, the segment interval for window and session stores is computed automatically as max(retentionPeriod / 2, 60_000ms) and is not configurable through the public API.

Changing retention requires a full state store restore. Because the segment interval is derived from the retention period, any change to retention also changes the segment boundaries. Since segment boundaries determine the on-disk directory structure and key layout, a retention change invalidates the existing state store data and requires restoring from the changelog topic. This is unnecessarily disruptive — a user who simply wants to keep data longer or shorter should not have to pay the cost of a full restore.

The default segment size is suboptimal for common access patterns. Many streaming applications need a long retention or grace period (e.g., 7 days) but access recent data the vast majority of the time. With the current formula, a 7-day retention produces segments of ~3.5 days. This means the active segment — the one receiving all writes and most reads — is very large, leading to heavier RocksDB compaction and lower cache-hit ratios. A user who knows their access pattern could benefit from smaller segments (e.g., 1 hour), keeping the active segment compact while still retaining historical data across many smaller segments.
