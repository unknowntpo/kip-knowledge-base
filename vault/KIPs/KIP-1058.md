## Summary

When the consumer enables isolation_level as READ_COMMITTED and reads a topic with no aborted/committed transactions, then the broker has to traverse all the local log segments to collect the aborted transactions in worst case since there won't be any entry in the transaction index. The search stops once it finds a segment with last-stable-offset higher than the FETCH request upper-boundary-offset.

The same logic is applied while reading the data from remote storage. In this case, when the FETCH request is reading data from the first remote log segment, then it has to fetch the offset, time, and transaction indexes of all the remaining remote-log segments, and then the call lands to the local-log segments before responding to the FETCH request which increases the time taken to serve the requests.

The EoS Abort Index design doc explains how the transaction index file filters out the aborted transaction records.
